# NetSentry-AI

Telecom Network Incident Triage Assistant

TRACK_ID=PS07

NetSentry-AI will:

1. Process network alerts.
2. Group related alerts into incidents.
3. Prioritize incidents.
4. Retrieve troubleshooting runbooks.
5. Generate evidence-backed recommendations.
6. Escalate unknown incidents to human engineers.

> Status: Steps 1–6 are in place — the FastAPI/static-dashboard scaffold, the
> data models, the network topology graph, a deterministic telecom alert
> generator with sample data, an alert processing and deduplication pipeline,
> and a deterministic correlation scoring engine. Prioritisation, runbook
> retrieval, recommendations and escalation are upcoming steps.

## Correlation Engine

NetSentry-AI uses a **deterministic, evidence-based correlation engine** rather
than an LLM to decide which alerts belong together.

Every alert pair is scored against four explicit signals:

| Signal | Points | Condition |
|---|---|---|
| **Same device** | +30 | Both alerts originate from the same node |
| **Topology relationship** | +20 | Devices are directly linked in `data/topology.json` |
| **Time proximity** | +20 | Alerts arrive within 5 minutes of each other |
| **Related alert types** | +30 | Types appear in the explicit relationship map |

Pairs reaching **≥ 60 points** are considered correlated.  A Union-Find
connected-components algorithm groups correlated pairs transitively, so a
cascade such as `CORE-R1 → SW-S1 → ACC-R3` is detected even when the end
nodes don't directly score above threshold with each other.

Every correlation result exposes its **score breakdown** for full
explainability:

```json
{
  "score": 70,
  "signals": {
    "same_device": 0,
    "related_device": 20,
    "time_proximity": 20,
    "related_type": 30
  },
  "explanation": "Correlation score: 70\nSame device: +0\nTopology relationship: +20\nWithin 5 minutes: +20\nRelated alert types: +30\nDecision: CORRELATED (threshold=60)"
}
```

## Sample alert data (deterministic)

`data/sample_alerts.json` holds a fixed, hand-authored alert fixture — no random
data, no external APIs, no live network traffic — so every demo behaves
identically. It is generated by `src/generator.py` and converted into the
`Alert` model from `src/models.py` on load.

| Scenario | Alerts | What it exercises |
| --- | --- | --- |
| `duplicate_alerts` | 10 | One CORE-R1 uplink failure reported repeatedly by four collectors (3 distinct fingerprints) — deduplication |
| `cascade_failure` | 26 | CORE-R1 → SW-S1/SW-S2 → ACC-R3/R4/R5/R6 failing within ~3.5 minutes — one major incident, correlation |
| `unknown_escalation` | 10 | 6 conditions with no runbook match (optical sync anomaly, PTP clock drift, unexpected protocol state changes, microloop, abnormal traffic, unmapped trap OID) + 4 unrelated alerts that should stay noise |

Alert types used: `LINK_DOWN`, `DEVICE_UNREACHABLE`, `HIGH_LATENCY`,
`PACKET_LOSS`, `AUTH_FAILURE`. Every alert carries `alert_id`, `timestamp`,
`device_id`, `device_name`, `device_type`, `alert_type`, `severity`, `message`,
`source` and `status`.

```bash
# Inspect the fixture
python -m src.generator --summary
python -m src.generator --scenario cascade_failure
python -m src.generator --scenario 3 --format json

# Regenerate data/sample_alerts.json from the scenario tables
python -m src.generator --write
```

```python
from src.generator import get_all_sample_alerts, generate_scenario
from src.processor import process_alerts
from src.scorer import correlate_processed_alerts

alerts = get_all_sample_alerts()                  # every scenario, as Alert models
processed, _ = process_alerts(alerts)             # deduplicate
incidents = correlate_processed_alerts(processed) # group into candidate incidents
```

> Note: the fixture reuses the devices from `data/topology.json`
> (`CORE-R1`, `SW-S1`, `ACC-R3` …) so generated alerts line up with the
> dashboard graph. In generic terms the cascade runs
> core → distribution (`SW-S1`/`SW-S2`) → access/edge (`ACC-R3`…`ACC-R6`).

Prioritisation, runbook retrieval and escalation are **not** implemented yet.
